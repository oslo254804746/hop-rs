# Hop v0.1.6

[简体中文](v0.1.6.zh-CN.md) | **English**

Released 2026-08-09.

v0.1.6 adds managed SSH remote commands and gives administrators a safe,
audited way to end live gateway sessions. It contains no database migration or
configuration-format change from v0.1.5.

## Highlights

### Managed remote commands

OpenSSH can now execute a command through an SSH asset selected by username:

```bash
ssh -p 2222 web-prod-01@hop-host 'uname -a'
printf 'input' | ssh -p 2222 web-prod-01@hop-host cat
ssh -tt -p 2222 web-prod-01@hop-host 'sudo systemctl status app'
```

Hop connects to the target with the credential assigned to that asset and
forwards stdin, stdout, stderr, exit status, exit signal, and an optional PTY.
Remote-command sessions do not enter the TUI or display the interactive Hop
banner. They are recorded with mode `exec`; command contents are deliberately
excluded from session audit data.

The same stable key-to-asset authorization used by interactive SSH, SFTP,
ProxyJump, and TCP forwarding is enforced before a command reaches the target.
Remote commands require a managed SSH asset with a usable credential.

### Live session controls

The Admin Web Audit Logs page identifies connections currently registered by
the gateway. Owners and Operators can terminate one live connection or all of
them. Viewers retain read-only visibility.

Termination covers TUI sessions, managed interactive SSH, managed remote
commands, SFTP, direct SSH, ProxyJump, and generic TCP relays. The session is
finished with status `terminated`, and the administrator action records actor,
source, target, result, and safe metadata in the audit log.

### Health reporting preserved

Managed SSH and direct TCP connection attempts continue to update real asset
health and latency data. Adding termination handling does not replace those
success and failure signals.

## Compatibility and upgrade

- No SQLite migration is added in v0.1.6.
- No configuration key is added or removed.
- Existing assets, credentials, authorized keys, Known Hosts, audit events,
  and sessions are preserved.
- A v0.1.5 deployment can be rolled back after a v0.1.6 binary-only upgrade,
  but a stopped-service backup is still recommended before every upgrade.

Treat Hop as access-critical infrastructure: arrange an alternate management
path, download and verify the artifact, stop Hop, back up the persistent data
and configuration, install v0.1.6, then verify Admin login and one real SSH
path. See the [deployment upgrade runbook](../deployment.md#upgrade).

Use the matching `.sha256` file before installing a downloaded artifact. For

with a floating tag.

## Known limitations

- Live-session registration is process-local; Hop does not aggregate sessions
  across several gateway instances.
- Session termination is immediate and does not ask the connected SSH client
  for confirmation.
- Command contents are not retained for replay or audit export.
- Local Admin passwords only; no OIDC.
- Audit filtering, pagination, export, and retention settings remain future
  work.
