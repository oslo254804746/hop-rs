# Hop Admin 改版总路线图

状态：Draft

设计稿：[Hop Admin — Product & UX Direction](https://www.figma.com/design/N2bXdpZomgzmICU164L6AH)
子方案：[轻量权限与多管理员方案](lightweight-access-control.md)

## 1. 目标与边界

本路线图合并以下工作：

- 现有 Admin Web 的登录、导航、Dashboard、资产和审计体验改进。
- 轻量“人员与访问”模型。
- 多管理员、Capability、审计证据和恢复能力。
- 后续 MFA、OIDC、API 与自动化能力。

产品目标不是把 Hop 变成重型 PAM，而是保持单二进制、SQLite 和快速上手，同时让生产环境中的访问可控、可解释、可恢复。

核心原则：

1. 单管理员和单人 SSH 使用路径保持简单。
2. 先使用用户任务语言，再使用安全领域术语。
3. 复杂能力按需出现，不在首次使用时要求配置组织、角色或策略。
4. Dashboard 只展示可解释、可行动的真实数据。
5. 所有高风险操作必须有身份、权限和审计证据。
6. 页面改版与底层权限演进分阶段发布，避免一次性重构全部 Admin Web。

## 2. 审计问题与计划映射

| 审计页面 | 当前主要问题 | 计划改动 | 所属阶段 |
|---|---|---|---|
| 登录 | 登录前展示完整导航；单一密码缺少稳定管理员身份 | 未登录时使用独立登录壳；保留单管理员密码习惯；多人模式才出现账号名 | Phase 1、5 |
| Dashboard | 标题重复；KPI 裁切；缺少健康、活动、风险和行动入口 | 改为 Gateway posture、关键指标、近期活动、风险待办和覆盖率 | Phase 3 |
| 资产 | 筛选、导出、批量操作和创建表单相互竞争；地址逐字换行 | 统一工具栏；创建/编辑使用 Drawer；保护目标地址列宽；完善批量状态 | Phase 1 |
| 审计日志 | 筛选标签不可操作；空状态无引导；缺少留存、导出和异常信号 | 真实查询筛选、分页、导出、留存说明、空状态和风险事件 | Phase 2、4 |
| 导航 | 导航按数据表组织，任务心智不够清晰 | 调整为 Overview、Inventory、Access、Trust、Observe、Operate | Phase 0 |
| 设置 | 只有本地密码，缺少恢复和安全状态 | 增加备份恢复、安全建议、身份登录和集成；按启用状态渐进展示 | Phase 2、6 |
| 全局 | 响应式、键盘、焦点和错误状态缺少统一约定 | 建立页面模板、组件状态和无障碍发布门槛 | Phase 0、7 |

## 3. 目标信息架构

### Overview

- 系统健康
- 近期访问活动
- 风险待办
- 控制覆盖率

### Inventory

- Assets
- Credentials

### Access

- People & Keys
- Admin Web Access
- Access Sets，仅在出现重复授权后展示

### Trust

- Known Hosts
- Credential Lifecycle

### Observe

- Sessions
- Audit Events
- Alerts，仅在存在告警能力后展示

### Operate

- Backup & Recovery
- Settings
- Identity Login，仅在启用多人或 OIDC 后展示
- Integrations，仅在存在集成后展示

未启用的复杂能力不占用一级导航位置。

## 4. 分阶段实施计划

目标：先统一页面结构和交互语言，降低后续每个页面重复返工。

### Phase 2：可信数据与安全底座

目标：先建立 Dashboard、审计和多人能力所需的真实数据，不制作只有视觉没有含义的卡片。

| ID | 任务 | 优先级 | 规模 | 验收标准 |
|---|---|---:|---:|---|
| ID-01 | 现有本地管理员迁移为稳定身份 | P0 | M | 原密码继续可用；升级过程无额外 onboarding |
| ID-02 | Admin session 绑定管理员 ID | P0 | M | 每个 Admin Web 操作可追溯到具体身份 |
| AUDIT-CORE-01 | 新增独立 `audit_events` | P0 | L | 记录登录、配置、资产、凭据、密钥和安全变更 |
| AUDIT-CORE-02 | 统一审计事件结构 | P0 | M | 包含 actor、action、target、result、source 和时间 |
| HEALTH-01 | Gateway 健康快照 | P0 | M | 提供 SSH/Admin 可达性和版本信息 |
| HEALTH-02 | 资产连接状态模型 | P1 | L | 区分未知、正常、失败和最近检查时间 |
| RECOVERY-01 | 备份状态记录 | P0 | M | 记录最近导出、最近验证恢复和失败原因 |
| COVERAGE-01 | 控制覆盖率计算 | P1 | M | 托管凭据、受限密钥、Known Hosts 均有可解释分母 |

Phase 2 发布门槛：

- 审计事件不会记录明文凭据、私钥或敏感表单内容。
- 现有 SQLite 数据可以无损升级。
- Dashboard 需要的数据有稳定查询接口和空状态语义。

实施状态（2026-07-28）：

- 已完成 `ID-01`、`ID-02`：升级迁移会创建稳定的本地管理员身份，既有单密码登录习惯保持不变，Admin session 已绑定管理员 ID 与展示名称。
- 已完成 `AUDIT-CORE-01`、`AUDIT-CORE-02`：独立 `audit_events` 覆盖登录、密码、资产、凭据、SSH 身份、Known Hosts 与批量导入，并在审计页与 SSH 会话分流展示。
- 已完成 `HEALTH-02` 数据底座：每个资产具有 `unknown` 初始状态；真实 SSH/托管连接与 TCP 转发会写入成功、失败、延迟和最近成功时间。
- 审计详情只保存白名单化元数据和错误分类，不保存密码、私钥、passphrase 或上传内容。
- `HEALTH-01` Gateway 快照与 `COVERAGE-01` 将在紧接其后的真实数据 Dashboard 切片中接入；`RECOVERY-01` 保留在恢复能力阶段。

### Phase 3：运营型 Dashboard

目标：让管理员打开 Hop 后立即知道系统状态、风险和下一步行动。

| ID | 任务 | 优先级 | 规模 | 验收标准 |
|---|---|---:|---:|---|
| DASH-01 | Gateway posture 横幅 | P0 | M | 汇总真实健康状态和需要关注的问题 |
| DASH-02 | 关键指标卡 | P0 | S | 资产、24h 会话、授权密钥和托管覆盖率不裁切 |
| DASH-03 | 近期访问活动 | P0 | M | 展示操作者、目标、模式、结果和持续时间 |
| DASH-04 | 风险待办队列 | P0 | M | 按恢复、安全和覆盖率排序，直接进入处理页面 |
| DASH-05 | 覆盖率与快捷操作 | P1 | M | 每个指标可解释并能进入对应详情 |
| DASH-06 | Dashboard 空状态 | P1 | S | 新安装时引导添加资产、凭据和 SSH 访问 |
| DASH-07 | 部分失败处理 | P1 | M | 单个数据源失败不会导致整个 Dashboard 不可用 |

禁止：

- 使用静态演示数字。
- 展示无法解释计算方式的安全分数。
- 将所有告警都标成高优先级。

实施状态（2026-07-28）：

- 已完成 `DASH-01` 至 `DASH-07`：Dashboard 使用真实数据库记录和运行态探测，不再展示静态演示数字。
- Gateway 状态包含 Admin/SSH 端点可达性、SQLite 健康、版本、启动时间和运行时间；资产健康来自真实 SSH/TCP 连接结果。
- 关键指标使用资产总数、精确 24 小时会话数、有效 SSH 身份数和托管 SSH 覆盖率。
- 近期 SSH 访问包含身份、目标、模式、结果和持续时间；近期管理变更来自独立 `audit_events`。
- 行动队列只根据数据源失败、连接失败/未知、托管凭据缺口和无有效 SSH 身份生成，并直接链接到处理页面。
- 托管凭据、受限 SSH 身份和 Known Hosts 覆盖率同时展示分子、分母和百分比；零分母保持可解释。
- 单个查询失败只降级对应区块并进入行动队列，不再让整个 Dashboard 返回错误页。

### Phase 5：人员、SSH 访问与多管理员

目标：在不引入重型 RBAC 界面的前提下支持小团队。

详细方案与研发任务见 [轻量权限与多管理员方案](lightweight-access-control.md)。

实施分为三个连续切片：

#### Slice 5A：人员与 SSH 访问

- 将密钥升级为“人员与访问”心智。
- 保留姓名、公钥、全部资产/选择资产的默认流程。
- 一个人可以拥有多个密钥。
- 不出现角色、策略或组织配置。

#### Slice 5B：Capability 授权边界

- 代码内部建立稳定 capability。
- 所有 Admin Web 写操作统一检查 capability。
- 权限不足页面说明任务影响和处理方式。
- UI 仍使用“完全管理、日常运维、只读查看”。

#### Slice 5C：第二个管理员

- 用户主动开启“允许进入管理后台”。
- 默认推荐日常运维。
- 存在多个管理员时，登录页才出现账号名。
- 禁用管理员后立即撤销会话。
- 保护最后一个完全管理员。

Phase 5 发布门槛：

- 单管理员升级前后主要路径不变。
- 新增 SSH 使用者时不展示角色或权限矩阵。
- 管理员可以快速判断某人能访问哪些资产、能否进入 Admin Web。
- 所有权限变更都有审计事件。

## 5. 推荐实现顺序

实现顺序按依赖和风险安排，不按页面顺序安排。

### 1. Phase 0：共享壳与组件约定

先解决导航、标题、工具栏、Drawer、表格和状态组件。如果跳过这一层，后续每个页面都会重复返工。

### 2. Phase 1：登录与资产高频修复

这是最快产生用户价值、且几乎不触碰权限模型的一批改动。完成后 Admin Web 的日常可用性会立即提升。

### 3. Phase 2：管理员身份、审计和健康数据

这是 Dashboard、多管理员和安全能力的共同底座。必须先于运营 Dashboard 和 RBAC/Capability 上线。

### 4. Phase 3：运营型 Dashboard

在真实健康、审计和覆盖率数据准备好后实现，避免上线只有视觉效果的空卡片。

### 5. Phase 4：审计工作台

复用 Phase 2 的 audit event 数据，提供查询、详情、导出与风险标记。

### 6. Phase 5A：人员与 SSH 访问

先改善当前密钥使用习惯，不同时开放多人后台，控制认知和迁移风险。

### 7. Phase 5B/5C：Capability 与第二个管理员

授权引擎先于多人入口；只有 capability、审计和会话撤销稳定后，才允许添加第二个管理员。

### 8. Phase 6：备份恢复、MFA 和 OIDC

先完成本地恢复闭环，再接入外部身份源。OIDC 不能成为唯一恢复方式。

### 9. Phase 7 与后续扩展

在各阶段持续做 QA；API、Webhook、配置即代码、资产发现和 HA 进入独立后续路线图。

## 6. 建议发布批次

### Release A：Admin Usability

包含 Phase 0、Phase 1。

用户可感知结果：

- 登录更干净。
- 资产列表可读。
- 创建和编辑不再挤压表格。
- 导航与页面操作一致。

### Release B：Trusted Operations

包含 Phase 2、Phase 3、Phase 4。

用户可感知结果：

- Dashboard 能显示真实健康和风险。
- 管理行为可追溯。
- 审计记录可以搜索和导出。
- 备份状态进入运营视野。

### Release C：Team-ready

包含 Phase 5。

用户可感知结果：

- SSH 访问按人员管理。
- 可以安全加入第二个管理员。
- 权限界面保持任务化，不出现复杂 RBAC 配置。

### Release D：Identity & Recovery

包含 Phase 6。

用户可感知结果：

- 可以验证备份恢复。
- 多管理员可以启用 MFA。
- 需要时可以接入 OIDC，并保留本地恢复入口。

## 7. 总发布原则

任何一个 Release 都必须满足：

- 可单独发布，不依赖尚未上线的假数据或隐藏后台操作。
- 升级不改变现有 SSH 连接方式。
- 单管理员不被迫理解多人、角色或身份源。
- 新增导航项必须对应可用任务，不展示“Coming soon”空入口。
- 失败状态提供恢复方向，不只显示错误码。
- 中英文、键盘、焦点、移动端和数据库迁移均进入验收范围。
