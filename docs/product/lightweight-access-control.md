# Hop 轻量权限与多管理员方案

状态：Team-ready local 基础已实现（2026-07-28）；用户研究与高级身份能力待后续验证

范围：Admin Web、多管理员、SSH 访问范围、后续 MFA / OIDC
产品原则：RBAC 是内部实现，不是用户必须学习的产品概念。

总路线图：[Hop Admin 改版总路线图](admin-redesign-roadmap.md)

## 1. 产品目标

Hop 的优势是单二进制、SQLite、本地运行和快速接入。权限能力必须加强生产可信度，但不能让第一次使用变成“先设计组织、角色和策略”。

目标体验：

1. 单人使用时，升级前后的主要路径不变。
2. 添加一个 SSH 使用者时，只需姓名、公钥和可访问资产。
3. 添加第二个管理员时，才出现管理权限选择。
4. 只有团队继续扩大或启用 OIDC 时，才出现组、身份源和高级控制。
5. 所有权限结果都用用户语言解释，例如“可访问全部资产”或“可管理资产和凭据”，不直接展示策略表达式。

## 2. 用户习惯与待验证假设

当前 Hop 已经形成的用户习惯：

- 管理员通过一个本地密码进入 Admin Web。
- SSH 使用者通过公钥识别，不需要额外账号密码。
- 公钥默认可以访问全部资产，也可以选择部分资产。
- 管理员主要围绕资产、凭据、公钥和会话完成任务。
- 部署者期望配置少、依赖少，并能直接查看 SQLite 数据和本地文件。

这些是根据当前产品路径得出的假设，不应直接当作真实用户研究结论。上线前安排以下验证：

- 访谈 5–8 名目标用户，覆盖个人维护者、小团队运维和审计/安全角色。
- 观察用户完成“添加同事并限制两台资产”的全过程，不先解释 RBAC。
- 记录用户使用的自然语言：更常说“给他这几台机器”还是“分配角色”。
- 验证三个权限预设是否足够，还是经常需要单项能力调整。
- 验证第二个管理员加入时，用户名、一次性设置链接和本地恢复密码是否可理解。

成功信号：

- 新增 SSH 使用者的中位完成时间不高于当前流程。
- 至少 80% 的测试用户不需要查看“高级权限”即可完成任务。
- 用户能准确复述新成员可以访问哪些资产、能否修改配置。

## 3. 交互模型

### 3.1 产品中不使用“RBAC”作为导航或主标题

用户看到的一级入口为“访问管理”，内部包含：

- 人员与密钥
- 管理后台访问
- 身份登录（启用 OIDC 后出现）
- 高级权限（存在高级配置时出现）

代码内部可以使用 role、capability、grant 等模型，但默认界面不暴露这些概念。

### 3.2 单管理员模式

默认保持现状：

- 首次启动仍生成一个本地管理员密码。
- 只有一个管理员时，登录页仍只要求密码，不额外要求用户名。
- 设置页显示“管理后台：仅你可以访问”，不展示角色配置。
- 访问管理页继续以公钥和资产范围为核心。

当用户主动点击“添加管理员”时，再解释多人模式会带来的登录变化。

### 3.3 添加 SSH 使用者

主按钮文案为“添加访问”，而不是“创建用户”或“分配角色”。

默认流程：

1. 填写姓名或用途，例如 `Alice`、`CI deploy key`。
2. 粘贴 SSH 公钥。
3. 选择访问范围：
   - 全部资产，默认选中。
   - 选择资产。
4. 查看一句话摘要并保存，例如“作为 SSH 使用者，可访问 3 台资产”。

“选择资产”展开后支持搜索、标签筛选和全选当前筛选结果。不要要求用户创建组。

### 3.4 添加管理员

在现有人员详情中提供“允许进入管理后台”开关，默认关闭。

开启后只展示三个任务型预设：

- 完全管理：可管理团队、安全设置和所有资源。
- 日常运维：可管理资产、凭据、公钥和会话，不能修改团队与安全设置。
- 只读查看：可以查看配置和审计记录，不能修改。

默认推荐“日常运维”。每个选项显示一行结果说明，不显示权限矩阵。

需要精细控制时，用户可以展开“查看权限详情”；第一版只允许查看预设包含的能力，不支持自定义角色。

### 3.5 登录渐进升级

- 只有一个本地管理员：保持密码登录。
- 存在多个本地管理员：登录页增加账号名，上次使用的账号可以被记住。
- 启用 OIDC：默认展示“使用组织账号登录”，本地恢复入口折叠在“其他方式”中。
- 第二个管理员创建成功后，提示启用 MFA，但不阻塞当前任务。

### 3.6 权限不足

不要只返回 `403 Forbidden`。

页面保留上下文，并说明：

- 用户刚才尝试做什么。
- 当前账号可以做什么。
- 谁可以处理，例如“需要完全管理权限”。
- 可复制的请求文本，例如“请允许我管理资产和凭据”。

## 4. 权限模型边界

### 4.1 第一阶段固定能力

建议代码内部使用 capability，而不是在路由中散落角色判断：

- `inventory.read`
- `assets.manage`
- `credentials.manage`
- `access.manage`
- `sessions.read`
- `audit.export`
- `settings.manage`
- `admins.manage`
- `recovery.manage`

三个内置预设映射到 capability 集合。预设名称可以迭代，数据库中保存稳定标识。

### 4.2 SSH 访问和 Admin Web 权限分开

- SSH 访问范围继续沿用 `all` / `restricted` 和资产关联表。
- Admin Web 权限由管理员账号和 capability 控制。
- 一个“人员”可以同时拥有 SSH 密钥和 Admin Web 访问，但两者生命周期独立。
- 禁用 Admin Web 登录不应自动删除 SSH 密钥，反之亦然。

### 4.3 第一阶段明确不做

- 自定义角色设计器。
- 可视化策略编排器或策略语言。
- 多层组织、项目、空间和资源继承。
- 嵌套用户组。
- 审批流、临时提权和 JIT Access。
- SCIM 自动同步。
- 强制迁移到外部数据库或集中式控制平面。

这些能力只有在真实用户需求出现后再进入路线图。

## 5. 版本拆分

### Milestone A：Team-ready local

目标：不改变单管理员习惯，让小团队能够安全地共享管理职责。

实施状态（2026-07-28）：

- 已完成渐进式本地多人登录：只有一位有效管理员时仍为密码直达；新增第二位后才出现账号字段，每位管理员使用独立密码。
- 已完成三个任务型访问预设、统一 capability 检查、权限不足解释页、最后一位完全管理员保护，以及账号停用或访问级别变化后的即时会话撤销。
- 已将“添加密钥”升级为“添加访问”流程，在姓名、公钥和全部/指定资产范围内一次完成；SSH 范围与 Admin Web 访问生命周期保持独立。
- 已补齐管理员创建、权限变化、登录与密码变化审计，并覆盖迁移、账号隔离、固定预设、受限资产写入和单管理员兼容测试。
- 本里程碑尚未实现 `people` 聚合实体、一个人员的多密钥详情页、审计筛选/导出、敏感操作重新验证和正式用户研究；这些任务继续保留，不以基础交付替代。

## 6. 推荐研发顺序

1. 先完成 `AUTH-01`、`CORE-02`、`AUTH-02`，让现有单管理员拥有稳定身份。
2. 实现 `CORE-03` 和 `TEST-01`，建立统一授权边界。
3. 完成 `AUD-01`、`AUD-02`，确保后续每个管理动作都可追溯。
4. 实现 `UX-02`、`CORE-01`、`UX-03`，把当前“密钥”升级为用户可理解的“人员与访问”。
5. 实现 `AUTH-03`、`UX-04`、`AUTH-04`、`AUTH-05`，开放第二个管理员。
6. 最后补齐筛选、权限不足状态、端到端与无障碍测试。

## 7. Milestone A 发布门槛

- 当前单管理员升级后无需额外配置。
- 新增一个 SSH 使用者在默认路径中不出现角色或权限矩阵。
- 管理员能在 10 秒内判断某个人可以访问哪些资产、能否进入 Admin Web。
- 所有 Admin Web 写操作都经过统一 capability 检查。
- 所有权限与管理员变更都有可检索审计记录。
- 最后一个 Owner、禁用账号会话、CSRF 和迁移兼容均有自动化测试。
- 不启用多人模式时，Hop 仍保持单二进制和 SQLite 的原有部署方式。
